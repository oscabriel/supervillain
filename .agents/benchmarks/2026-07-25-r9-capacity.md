# R9 capacity benchmark — the run the caps come from

Measured 2026-07-25 for [#60](https://github.com/oscabriel/supervillain/issues/60), implementing [ADR-0012](../adr/0012-outbound-only-hybrid-drop-iroh-host-dials-out.md) NQ-10 (protective caps) and NQ-14 (the production PTY cap).

ADR-0012 pins that **no cap number and no public capacity claim precedes this benchmark**. This document is what unpins them. Everything in `apps/gateway/src/capacity.ts` is read off the run below; anything not read off it is still a placeholder and should say so.

## The harness

```
bun run bench:gateway-capacity                       # the full matrix
bun run bench:gateway-capacity -- --sessions 1,10 --workloads idle,chat
bun run bench:gateway-capacity -- --seconds 20 --json results.json
```

Source: `apps/gateway/bench/` — `capacity.ts` (the driver), `gateway-process.ts` (the gateway under test), `bench-room.ts` (the Host's Room), `seats.ts` (one SSH seat), `protocol.ts` (the line protocol between the two processes).

Shape of a run:

- The **gateway runs in its own process** and samples its own `process.cpuUsage()` and RSS on request. That separation is the whole reason the numbers mean anything: a hundred SSH clients in the same process would put their cost inside the gateway's.
- The **Host** is an in-memory Room served over a real `room-wire` pipe on a real `transport-ws` connection (plaintext on loopback — TLS is #64's, and its per-byte cost is not what this matrix is about). It is not a real `room-host`: the lattice forbids the gateway package from importing it, and a real log would put disk I/O inside a gateway measurement.
- Every **seat is a real SSH session** with a real key and a real PTY, opened through `ssh2`, joining by username exactly as a player does.
- **Every cell gets its own gateway process and its own Room inside it.** The fold's history is the gateway's and every arrival replays all of it, so a reused Room would have the sixteenth cell joining a Room with fifteen cells of backlog — and a reused _process_ turned out to be worse than that (see the last section).

Workloads:

| workload | what the seats do | what it is for |
| --- | --- | --- |
| idle | nothing at all; nothing is posted either | NQ-14's measurement of a gateway with no ambient `renderer.start()` |
| chat | each seat types a line every 2 s | the fan-out shape: one line, every seat redraws |
| map-pan | each seat pans a loaded battle map ~7×/s | the expensive one — per-seat FrameBuffer diffing, no Host traffic at all |
| slow-reader | a quarter of the seats never read their channel; the Host posts 10×/s | NQ-5's isolation: the fast readers must be unaffected |

## What the numbers say

**Idle is genuinely idle (NQ-14).** A hundred seats sitting on a gateway with no ambient `renderer.start()` cost **0.25 of one core in total** — 2.5 ms of CPU per seat per second — and the 1-seat figure (9 ms/s) is the process floor rather than a per-seat cost. This is the number NQ-14 refused to let anyone assume, and it says the ambient-render removal did what #56 claimed. Memory is the real per-seat cost at rest: about **5.5 MiB of RSS per idle seat** over a ~114 MiB floor.

**The gateway's ceiling is one thread.** Every heavy cell plateaus at 1130–1170 ms/s. That is the single JS thread plus its GC, saturated: the box has sixteen of them and the gateway can use about one. So capacity per gateway process is bounded by _one core_, not by the box, and a busy Room is what fills it.

**Chat fan-out is what actually costs.** One line typed is one redraw on every seat in the Room, so cost grows with the square of the Room. It does not _show_ as a square because the renderer coalesces frames when it falls behind — the cost lands on latency instead. Key-to-frame p95: **45 ms at 10 seats, 151 ms at 50, 480 ms at 100.** That curve is the whole argument for a sessions-per-room cap.

**Map-pan is cheaper than expected, per keystroke.** Panning writes only the changed cells, so a panning seat costs ~1.2 KiB/s and 12–25 ms of CPU per seat per second at 120×40. p95 stays under 90 ms up to 50 seats.

**Joining is expensive, and it gets worse as a Room fills.** Seating 100 players costs the gateway 15 s of CPU — 153 ms each, three times the per-seat cost at 10. Every arrival replays the Room's history through its own render. This is a second, independent argument for the same cap, and it is the one to watch when a table's log is long.

**The single Host pipe is nowhere near saturation (NQ-2).** The busiest cell put **~29 KiB/s** over the one pipe — 17 KiB/s up, 12 KiB/s down, for a hundred seats in a chat-heavy Room. NQ-2's reopening trigger is a measurement, and this measurement does not come close to reaching it: WebSocket over TLS stays, and there is nothing here to argue about.

**Per-session isolation held, and it was not really tested.** No fast reader was ever dropped (`closed 0/0` everywhere), and the fast readers' latency in slow-reader cells tracks the chat cells at the same seat count, so a quarter of the Room reading nothing cost the rest nothing measurable. But no slow reader was dropped either, and that is the honest caveat: a seat that stops reading is bounded first by its SSH channel window (~2 MiB), and at the ~0.7–5 KiB/s a seat actually produces, filling it takes **minutes**, not the ten seconds a cell lasts. The drop mechanisms are exercised in `apps/gateway/test/capacity.test.ts` instead, where a fake channel can stall on demand.

**The fold's envelope budget never fired, and it never will for this case.** ADR-0012's per-session budget (NQ-5) drops a _view_ whose consumer lags. A seat's consumer is its renderer, which takes every envelope the instant it arrives and writes a frame — so a client that stops reading its socket never lags its cursor. That gap is why this issue added the **byte and stall halves** of the per-session output budget, in `attachSshChannel`. The envelope budget still guards a genuinely slow consumer; it is not the thing that catches a dead client.

## The caps this run chose

All of them live in `apps/gateway/src/capacity.ts` and every one is settable from the environment (`supervillain gateway serve --help` lists them). They are cost ceilings and abuse protection, never monetization, and outgrowing them has a free exit: run the same binary yourself.

| cap | default | read off |
| --- | --- | --- |
| `sessionsPerRoom` | **32** | the knee in key-to-frame p95 — 45 ms at 10 seats, 151 ms at 50, 480 ms at 100. 32 sits at roughly 100 ms, below the point where typing feels laggy, and keeps one Room from filling the gateway's single thread (chat at 50 seats already takes 93% of it). Seating cost agrees: 88 ms of gateway CPU per arrival at 50 seats against 48 ms at 10. |
| `roomsPerIdentity` | **8** | an attached Room with no seats costs ~0.35 KiB/s of pipe traffic and no measurable CPU, so this is not rationing a resource that hurts — it stops one identity parking hundreds of folds on a shared box. A GM runs one. |
| `sessionBudget` | **512** envelopes | unchanged, and it never fired in this matrix. It guards a slow _consumer_, which a rendering seat is not. |
| `sessionOutputBytes` | **4 MiB** | a healthy seat leaves under 5 KiB/s unwritten and the SSH channel window itself is ~2 MiB; 4 MiB of unflushed output is roughly fifteen minutes of a seat's entire output, so nothing healthy reaches it. |
| `sessionStallMs` | **30 s** | a healthy seat's write callback lands in single-digit ms at every point in this matrix. 30 s is three orders of magnitude of headroom, and it bounds a client that vanished without closing its socket. |
| `pty` | **300×100** | below `@opentui/ssh`'s own 500×200, as NQ-14 requires. Seats here were 120×40 = 4800 cells; 300×100 is 6.25× the area (500×200 would be 20.8×) and render cost tracks area, so the cap holds the worst-case seat to about six times the measured one rather than twenty. An oversized terminal gets the capped render plus an honest notice, never a refusal. |

Lobby idle/max timeouts and the per-IP connection window keep ADR-0008's floors (5 min idle, 30 min hold, 30 connections/min per IP) — they are anti-squatting numbers, not capacity, and nothing here moves them. They became environment-settable with the rest.

**One box, roughly.** At these caps: one gateway process ≈ one core ≈ a few dozen active seats spread over its Rooms, with ~5.5 MiB of RSS per idle seat and ~8.5 MiB per busy one over a ~115 MiB floor. #40's one-box sizing should start from "a gateway wants a core and a gigabyte for a hundred seats", then add the web backend, which this measures nothing of.

## Reopening triggers, stated against these baselines

A future regression has to be comparable to something, so each trigger names a number from the run above.

- **`sessionsPerRoom` moves** when key-to-frame p95 at the cap is measured above **250 ms** on the hosted box (baseline: ~100 ms at 32 seats, interpolated between 45 ms at 10 and 151 ms at 50), or when gateway CPU with one Room at the cap sustains above **80% of one core** (baseline: 926 ms/s at 50 chat seats, 1160 ms/s saturated).
- **`roomsPerIdentity` moves** when an attached, seatless Room is measured costing more than **5 KiB/s** of pipe traffic or any measurable CPU (baseline: 0.35 KiB/s, no measurable CPU).
- **`sessionOutputBytes` / `sessionStallMs` move** when a healthy seat is measured leaving more than **1 MiB** unwritten, or a write callback taking longer than **1 s**, in ordinary play (baselines: under 5 KiB/s per seat, single-digit ms per write). Player reports of being dropped mid-session are the other signal, and they are the one to take seriously first. _(Superseded 2026-07-25, [#62](https://github.com/oscabriel/supervillain/issues/62): `attachSshChannel` — the mechanism these two numbers tuned — was retired when the Door adopted `@opentui/ssh`, whose channel writes wait for the peer to drain, so a dead reader parks its own frame feed instead of growing a buffer. Nothing drops a vanished seat any more; the exposure is bounded by `sessionsPerRoom` and the door's global session cap, and the residual gap is flagged on #62. This trigger now reopens against the library's backpressure, not a gateway knob.)_
- **`sessionBudget` moves** when a `view-dropped` event is seen in production at all (baseline: zero across this matrix). Its firing would mean a consumer that lags, which is a different bug worth reading before the number moves.
- **The PTY cap moves** on a measured PTY-size sweep, which this run did not do — every seat here was 120×40. Raising it past 500×200 is not available; `@opentui/ssh` owns that ceiling.
- **NQ-2 (WebSocket over TLS) reopens** when the single Host pipe is measured above **~1 MiB/s sustained**, or head-of-line stalls are attributed to the transport (baseline: 29 KiB/s at the busiest cell — a factor of thirty-five below the line). Nothing short of a measurement reopens it.
- **The whole document expires** when `apps/gateway` changes how it renders per seat. The render path is what every number here is made of; a change to it makes this run history rather than a baseline. Re-run the harness and date a new file.

## The one thing this run found that is not a number

The first attempt at this matrix reused **one** gateway process across all sixteen cells. From the fourth cell onward its CPU sat pinned at ~1.15 cores and its RSS never fell back between cells — the 1-seat map-pan cell read **1135 ms/s and 214 ms p50** on the shared process against **117 ms/s and 4 ms p50** on a fresh one. Same code, same workload, an order of magnitude apart.

So: after Rooms detach and sessions close, a gateway process does not obviously return to rest. That is either residue worth fixing or a measurement artefact of how the harness tears seats down, and this benchmark cannot tell which — it is the wrong instrument. It wants its own issue: seat and unseat a Room repeatedly on one long-lived gateway and watch RSS and CPU at rest between rounds. Until then the harness gives every cell its own gateway process, which is the right thing for a capacity matrix regardless.

## What this run does not measure

- **TLS.** The pipe ran plaintext on loopback. #64 owns the certificate story; the per-byte cost of TLS on the pipe is unmeasured.
- **A real Host.** The Room is in memory in the harness process. Host-side log I/O, real `decide` cost, and a real campaign folder are all absent — by design, since this measures the gateway.
- **Network.** Everything is loopback. Real players arrive over the internet, where every latency above is a floor and the per-seat write costs are larger.
- **The web backend.** #40's one-box sizing has to add whatever `apps/web` costs; this is the gateway alone.
- **Sustained hours.** The longest window here is tens of seconds. Leak behaviour over a day's play is unmeasured.
