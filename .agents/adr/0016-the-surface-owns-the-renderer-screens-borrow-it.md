# The surface owns the renderer; screens borrow it

Resolved in the 2026-07-25 grilling session over the burndown's open questions, against [#62](https://github.com/oscabriel/supervillain/issues/62) (blocked on exactly this), [#56](https://github.com/oscabriel/supervillain/issues/56) (which built the renderer factory seam and explicitly left ownership unsettled) and [#67](https://github.com/oscabriel/supervillain/issues/67) (whose lobby is the first multi-screen surface). The conflict that forced the decision: `@opentui/ssh` creates **exactly one renderer per SSH connection** (`attachRenderer` memoises; read at the pinned clone, `packages/ssh/src/bridge.ts:309`) and unconditionally wires the renderer's `DESTROY` event to tearing down the whole session (`bridge.ts:332`) — to the library, renderer death _is_ session death. Our screens meanwhile use `renderer.destroy()` to mean "this screen is finished": the lobby (`packages/table/src/lobby.ts`) and the table chrome (`packages/table/src/chrome.ts`) each mint a renderer on entry and destroy it on exit, and `serveShell` loops lobby → room → lobby on one connection. Merged as they stand, a visitor leaving the lobby's first screen would kill their SSH session. The integrator correctly aborted the [#62](https://github.com/oscabriel/supervillain/issues/62) merge rather than land that.

**Decision: whoever creates the renderer destroys it — the surface owns the renderer's lifetime, and a screen never calls `renderer.destroy()`.** A _surface_ is the thing that owns the connection: the Door for an SSH session, the CLI process for a local TTY. The surface mints (or, under `@opentui/ssh`, receives) one renderer per session and destroys it exactly once, when the session ends. A _screen_ — lobby, table chrome, and any future surface content — borrows the renderer, adds its renderables to the root, removes them on the way out, and signals "I'm done" by resolving its returned promise. This is the ordinary ownership rule for any resource, and it is the model the library was designed around; no fork, no wrapper, no patched dependency.

**Rejected: fighting the library.** Wrapping or forking the bridge so `destroy` does not end the session would mean patching a pinned dependency to preserve a calling convention we invented, and `SessionBridgeOptions.createRenderer` is an internal test seam (`ServerConfig` does not expose it), so there is no supported injection point anyway. **Rejected: one renderer per screen.** Incompatible with the bridge's one-renderer-per-connection memoisation without the fork above, and it buys nothing — a fresh renderer per screen was always an implementation accident, not a design.

**Consequences:** `runLobby` and `runChrome`/`runTable` change shape: each takes the renderer (not a factory), drops its internal `teardown()`-calls-`destroy()` (`lobby.ts:162-166`, `chrome.ts:404-408`), and instead detaches its own renderables and resolves. `TableRendererFactory` moves up a level: the surface calls it once per session (`serveShell` reuses the one renderer across every lobby and table round; the local CLI path mints once before its loop and destroys after). Screen-exit-by-`destroy()` stops being load-bearing anywhere. Branch `wf/issue-62` is re-run against a base containing this change and [#67](https://github.com/oscabriel/supervillain/issues/67); its worktree and tests are intact.

**Revisit triggers:** a surface that genuinely needs to swap renderers mid-session (none is imaginable under `@opentui/ssh`'s one-per-connection model — this would first be a library conversation); a screen with cleanup so entangled that detaching renderables is not enough, which would be evidence the screen is holding resources that belong to the surface.
