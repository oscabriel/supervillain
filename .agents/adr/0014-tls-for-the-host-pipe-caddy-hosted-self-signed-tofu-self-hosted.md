# TLS for the Host pipe: Caddy terminates hosted, a self-signed certificate and a pinned fingerprint self-hosted

Resolved on [TLS for the Host pipe (#64)](https://github.com/oscabriel/supervillain/issues/64), 2026-07-25. [ADR-0012](./0012-outbound-only-hybrid-drop-iroh-host-dials-out.md) decided the pipe is **WebSocket over TLS** (NQ-2) and that a self-hosted gateway "mints a self-signed cert whose fingerprint travels in the Host-onboarding pairing code — no CA, domain, or reverse proxy ever required" (NQ-9). The first pass of pivot issues shipped the pipe with neither: there was zero TLS, certificate, or fingerprint code in the repo. This ADR records the half NQ-9 left implicit — **where TLS ends on the hosted box** — and the shape of the pairing code, because both determine what a self-hosted operator has to reproduce.

**Decision: on the hosted gateway, TLS terminates at Caddy.** [#40](https://github.com/oscabriel/supervillain/issues/40) already gives Caddy 80/443 on the one box with auto-ACME, and holds the web backend to localhost; the pipe joins that arrangement as one more reverse-proxied upstream, and the gateway process binds the pipe on loopback with no certificate of its own. The alternative — the gateway terminating its own TLS on the apex — needs either a second port carrying its own ACME client alongside Caddy's, or SNI passthrough through Caddy, which #40 already priced as a custom xcaddy build owned forever. Terminating at the edge costs one config stanza and reuses a renewal path that is already monitored. **The self-hosted operator reproduces none of this**: posture 2 is the in-process path below, so "no reverse proxy is ever required" survives literally rather than by exception. Accepted cost: two TLS paths exist in the product, and only the in-process one is exercised by our own deployment — so the in-process path is covered by tests rather than by production, and the terminated-upstream mode is a named, explicit setting (`SUPERVILLAIN_GATEWAY_TLS=terminated-upstream`) that an operator chooses rather than falls into.

**Decision: the gateway's TLS posture is one of three named modes, and the default is `self-signed`.** `self-signed` mints a P-256 certificate on first start, keeps it in the state directory, and terminates TLS in-process. `terminated-upstream` binds plaintext for a proxy in front. `files` terminates in-process with an operator-supplied certificate. The default is the self-hosted one deliberately: a gateway binary started with no arguments must not carry production traffic in the clear, and an unrecognised mode is a startup refusal rather than a fall back to the default, because "is this traffic encrypted" is not a question an operator should have to infer. Two consequences follow from the mode rather than from separate settings: the pipe binds `0.0.0.0` when this process is the TLS edge and `127.0.0.1` when it is not, and the pipe port defaults to **8443** when it is the edge — the one port a homelab operator forwards. 8443 is a tunable default, not a protocol constant; 443 belongs to Caddy on the hosted box.

**Decision: the certificate is minted in-process, with no OpenSSL binary and no new dependency.** Neither `node:crypto` nor Bun exposes a certificate builder, so `packages/transport-ws` writes the X.509 DER by hand (`asn1.ts`, `certificate.ts`, ~200 lines, write-only — the only reader we ever face is a TLS stack). Shelling out to `openssl` was rejected because a homelab operator's ritual is "one forwarded port plus dynamic DNS" and must not silently grow a toolchain; a JS certificate library was rejected as a dependency carried into the compiled binary for one function. The certificate is **persisted** in the gateway's state directory and reused across restarts — a certificate re-minted per start would refuse every Host that had ever paired, which is the loud failure trust-on-first-use exists to raise and precisely the wrong thing to raise at ourselves. Its subject and subjectAltName are cosmetic: a self-signed gateway is identified by its fingerprint and by nothing else, since NQ-9 promises there is no domain to check.

**Decision: the pairing code is the gateway URL with its fingerprint in the fragment** — `wss://box.example:8443#fp=sha256:<64 lowercase hex>`. One pasteable string, and a **superset of the plain URL** `--gateway` already takes: [#57](https://github.com/oscabriel/supervillain/issues/57) owns the URL half, this owns the fingerprint that rides alongside it, and nothing about the flag or the environment variable had to change. A fragment was chosen over a query parameter (`?` is a glob character in zsh; `#` mid-word is literal in both zsh and bash) and over an opaque `sv1_<base64>` token (which hides the address from the human pasting it). **A fragment that is not a fingerprint is a parse refusal, never an ignored suffix** — a fingerprint the reader silently drops is the one failure trust-on-first-use cannot survive. A bare URL with no fragment means CA trust, which is what a hosted or `files`-mode gateway hands out; a `files`-mode gateway deliberately publishes **no** fingerprint, because a real certificate is expected to be renewed and a pin would turn every renewal into a refusal.

**Decision: the pin is per-machine config, written only after a connection succeeds, and never overridden by a prompt.** Pins live beside the machine key in `~/.config/supervillain/gateways.json`, keyed by scheme+host+port, recording the fingerprint and when it was first trusted — credentials and trust decisions belong to the machine, never to the campaign folder that moves between machines (ADR-0012, NQ-3). Three rules make the store meaningful. A pin is written **after** the pairing code has proved itself against a live gateway, so a code that never connected leaves nothing to un-pair. A **pin always wins over a bare URL**, so dropping the fragment cannot quietly downgrade a pinned gateway to whatever a CA will vouch for. And a fingerprint that disagrees with the pin — whether it arrives in a pairing code or is served by the gateway on the wire — is a **refusal that names both fingerprints and the file holding the decision**, never a prompt-and-continue. That refusal is the entire value of trust on first use.

**Decision: a trust failure stops the redial loop; `room-wire` gains the seam error that lets it.** ADR-0012 NQ-6 has the Host redialing forever with backoff, which is right for an unreachable gateway and catastrophic for a gateway serving the wrong certificate — an infinite quiet retry is a silent continue wearing a different hat. `room-wire` therefore names `TransportTrustError` on the transport seam and halts on it exactly as it halts on a registration refusal; `transport-ws` raises a subclass. The seam learns nothing about certificates: NQ-13's "`room-wire` imports no transport package" holds, and the rule is stated as _redialing cannot fix this_, which any future adapter can mean.

**Decision: verification happens before the WebSocket exists.** A pinned dial first opens a throwaway TLS connection, reads the served certificate, and compares its fingerprint; only then does it open the WebSocket, trusting **that exact certificate** as its sole anchor. Nothing of ours is sent to an unverified gateway, and a certificate swapped in between the two steps fails the second handshake rather than sneaking through. The reason it is two steps rather than an inline check is portability: Bun and Node's WebSocket clients disagree about TLS options and about whether the peer certificate is reachable at all, while `node:tls`'s `getPeerCertificate()` is identical on both — and the dual Bun/Node lane (NQ-12) is a CI gate, not a preference. The client half moved from the global `WebSocket` to the `ws` package for the same reason. Accepted cost: one extra TLS handshake per dial on the pinned path, on a connection that reconnects at human timescales.

**Decision: plaintext survives for loopback development and warns everywhere else.** `ws://` still works — #57 developed the pipe over it — but dialing a non-loopback host in the clear prints a warning naming what crosses the network. Refusing outright was rejected as scope beyond the issue's acceptance; leaving it silent was rejected because a development default that quietly reaches the internet is how interim states become permanent. **The sequencing constraint from #64 stands: no public gateway is deployed before this closes.**

**Consequences:** `packages/transport-ws` gains `asn1.ts`, `certificate.ts`, `fingerprint.ts`, and `pinning.ts`; its listener gains a `tls` option and reports a certificate fingerprint; its dialer gains `certificateFingerprint`. `packages/room-wire` gains `TransportTrustError` on the seam and halts on it. `apps/gateway` gains `tls.ts` (mode resolution, certificate persistence, pairing-code assembly) and prints a pairing code — or, behind a wildcard bind with no advertised URL, the fingerprint plus the one variable that completes it, because a code naming `0.0.0.0` is worse than no code. `apps/cli` gains `gateways.ts` (the pin store and the resolution rules). The hosted deploy gains a Caddy stanza reverse-proxying the pipe and must set `SUPERVILLAIN_GATEWAY_TLS=terminated-upstream`; #40's firewall inventory gains no port on the hosted box and one forwarded port in the self-hosted recipe. ADR-0013's reading of #64 — a fingerprint pinned by our own CLI, unavailable to browsers — is confirmed by construction, so posture 2b's domain requirement is unchanged.

**Revisit triggers:** in-process TLS on the hosted gateway only if Caddy stops being the right edge for the web surface; a second fingerprint algorithm only on a SHA-256 weakness, and the pairing code already names the algorithm so that is a parse branch; a deliberate re-pairing affordance (rather than "remove the entry from this file") the first time a real operator rotates a gateway certificate; refusing non-loopback plaintext outright if the warning proves ignorable; the 8443 default if it collides with something common in the homelab cohort.
