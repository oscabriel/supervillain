# Key linking: CLI-minted codes, backend registry as truth, gateway as conduit, linking events in the log

Resolved on [Key linking and guest adoption flow (#34)](https://github.com/oscabriel/supervillain/issues/34), 2026-07-20. The definition made linking launch-tier (§Identity across surfaces) but never mechanized it: where codes are minted and redeemed, where identity equivalence lives, and how a room whose log is offline learns that two actors became one person.

**Amended 2026-07-25 by [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md) — this document's title is now wrong.** The equivalence graph is **gateway-owned**, not backend-owned: it lives in the gateway's SQLite, so identity resolution and revocation are local reads that work with no company backend in existence (ADR-0012's NQ-9 makes the self-hosted gateway one binary with no backend, which this ADR's original home for the graph could not serve). Three mechanism changes follow, marked inline below: `key link` targets the **gateway** rather than the backend; the gateway **mints guest adoption codes itself**; and "pending linking events" are **derived on demand from the graph, never queued** — no per-room delivery state exists anywhere. Every other decision here stands unchanged, including the `core.actor-linked` event, the fold's union of `envelope.actor` with `payload.linked`, and delivery over the registration connection.

**Decision: linking is terminal-only, and the CLI is the sole mint/redeem surface.** The trusted key mints; the new key redeems. No browser leg (a QR/web flow would smuggle in the web auth surface the definition excludes at launch) and no in-room linking UI. The CLI surface follows #28's noun pattern — a `key` noun, one entry point: `supervillain key link` on an established device mints and prints a code; `supervillain key link <code>` on the new device redeems it. Redemption accepts either code kind (the backend knows what a code maps to), so the guest upgrade box needs exactly one line of instruction. CLI first-run setup offers the same call conversationally. Device-link codes are single-use, 15-minute expiry (both machines are at hand). The CLI reaches the backend over the same authenticated-HTTP path `publish` needs — shared machinery. _(Correction 2026-07-25, [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md): `key link` targets the **gateway**, which owns the graph and the codes. `publish` still targets the backend, so the two verbs no longer share one destination — they share the authenticated-HTTP shape.)_

**Decision: guest adoption codes are minted at session start and shown in the upgrade box.** Only the gateway knows a session is `guest:X`, and guests have no reconnect continuity (ADR-0003), so the handle must be minted during the live session: the gateway (as trusted party) has the backend mint a single-use adoption code bound to `guest:X` _(Correction 2026-07-25, [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md): the gateway **mints the code itself** — it owns the graph and the code table, so the backend hop is gone; this is also the only shape that works self-hosted)_, and the can't-miss upgrade box displays it — install the CLI, `supervillain key link <CODE>`, keep tonight's history. Adoption codes live **7 days** (guest-first means no mid-session install pressure) at ~8–10 base32 chars of entropy; the guarded asset is one session's chat and rolls. A guest may instead just bring a key next time (ADR-0003's path, unchanged) — continuity going forward, no adoption until they install the CLI and link.

**Decision: the backend registry is the truth; rooms materialize linking as log events.** _(Corrected 2026-07-25, [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md): **the gateway registry is the truth.** The graph lives in the gateway's SQLite next to the name registry and the ADR-0008 prefs table. Both deployables must resolve key → identity — the gateway on the authentication path, the backend to key artifacts by owner — and only the gateway's copy survives the no-backend self-hosted posture; the backend reads identity through an interface. Note this also resolves an inconsistency that already existed: closed ops ticket [#40](https://github.com/oscabriel/supervillain/issues/40) had listed the key-linking graph in the gateway's registry DB. The second half of this decision — rooms materialize linking as log events — is unaffected.)_ The backend service (which the definition already makes the code registry) holds the authoritative key-equivalence graph. But seats and attribution are log-derived and a joiner's fold must equal the host's, so any equivalence that affects a room must land in that room's log: a `core.actor-linked` event whose envelope actor is the redeeming key and whose payload names the absorbed actor (`{ linked: "guest:X" | "<64hex>" }`). The fold unions `envelope.actor` with `payload.linked`; one event type serves adoption and device linking alike. Historical events are untouched — old `guest:X` entries stay raw; the fold makes them reachable (prototype-validated). The event arrives as a **gateway-stamped submission** — actor ≠ connection is exactly the trusted-stamper power ADR-0003 grants.

**Decision: linking facts travel over the registration connection.** At room registration the gateway delivers pending linking events for the room's actors (the redeemed-on-Tuesday case) _(Correction 2026-07-25, [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md): **derived, not queued.** The Host sends its own actor list at registration and the gateway answers from the graph; no per-room queue, delivery bookkeeping, or acknowledgement state exists. The graph is already the complete truth, so a queue would be a staler second copy of a computable fact — and this is what keeps ADR-0012's "no durable game state at the gateway" a clean line.)_; when an unknown key joins, the host queries the gateway over that same connection — linked to anyone in my log? — appends the event, and seat claiming proceeds. No new trust relationships and no host→backend channel: an unregistered room trusts nobody and therefore links nobody, consistent with ADR-0003. GM roaming falls out with no mechanism of its own: the laptop key unions into the GM's identity, and idempotent log-derived seat claiming returns the GM seat.

**Consequences:** the registration protocol grows two duties (pending-linkings delivery, unknown-key lookup); the gateway becomes the bridge between the two deployables for identity data — how gateway and backend share the registry is an internal seam deliberately left to the backend-data-layer decision ([#32](https://github.com/oscabriel/supervillain/issues/32)) _(resolved 2026-07-25, [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md): the gateway owns the graph; the backend reads it through a narrow interface with local and remote implementations)_; the CLI gains a `key` noun and an authenticated backend path.

**Revisit triggers:** passkeys (v3) join the same equivalence graph via the same primitive — if the browser session can't be modeled as one more linked key, that is a definition problem, not a patch here. Unlink/revoke is deliberately undesigned at v1 (nothing in the definition requires it; a compromised key demands it eventually — definition patch, not a hack). _(Superseded 2026-07-24 by [ADR-0012](./0012-outbound-only-hybrid-drop-iroh-host-dials-out.md) NQ-3, which graduates revocation to **required** because an always-on homelab box makes key compromise real; and located 2026-07-25 by [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md): revoked state is a column in the **gateway** store, so refusal is a local read that works with our servers unreachable. Tracked on [#59](https://github.com/oscabriel/supervillain/issues/59).)_ Guest reconnect-as-same-guest remains deliberately absent per ADR-0003.

**Amended 2026-07-25, after [#66](https://github.com/oscabriel/supervillain/issues/66) — five semantics the implementation had to settle, ratified in the grilling session over the burndown's open questions.** (1) **Merging two established identities is refused.** A key that already holds its own identity — sibling keys or owned rooms — cannot redeem a device code; the refusal says to link a fresh key or move that identity's rooms first. A silent merge would transfer or orphan room ownership; a lone key owning nothing is silently moved, which is the union this ADR always meant. (2) **Linking two actors who each hold a seat at the same table yields one identity holding two seats**, and seat lookup answers the earlier seat in log order — the only deterministic, replay-stable reading. Whether the seats should ever merge is a table-rules question no evidence has raised. (3) **A lost adoption code has no recovery path.** It is shown once in the upgrade box, never again; that is what single-use means, and the guarded asset remains one session's chat and rolls. (4) **Device-link codes are 8 Crockford base32 characters (~40 bits).** Both machines are at hand and the code lives 15 minutes; adoption codes keep this ADR's ~10 characters. (5) **`key link` rides the authenticated Host pipe (`transport-ws`), not HTTP** — the gateway exposes no HTTP surface, the pipe is already mutually authenticated ([ADR-0017](./0017-the-v1-pipe-handshake-is-ratified.md)), and ADR-0013 had already softened "same path as publish" to "same shape". Two gaps found beside these are follow-up work, not ratified behaviour: a device code minted by a key that is _later revoked_ stays redeemable for the rest of its TTL, and `core.link-actor` reaches the room's submit path before any seat or authority check with nothing stating that only a gateway stamp may carry it — one security issue tracks both.
