# Key linking: CLI-minted codes, backend registry as truth, gateway as conduit, linking events in the log

Resolved on [Key linking and guest adoption flow (#34)](https://github.com/oscabriel/supervillain/issues/34), 2026-07-20. The definition made linking launch-tier (§Identity across surfaces) but never mechanized it: where codes are minted and redeemed, where identity equivalence lives, and how a room whose log is offline learns that two actors became one person.

**Decision: linking is terminal-only, and the CLI is the sole mint/redeem surface.** The trusted key mints; the new key redeems. No browser leg (a QR/web flow would smuggle in the web auth surface the definition excludes at launch) and no in-room linking UI. The CLI surface follows #28's noun pattern — a `key` noun, one entry point: `supervillain key link` on an established device mints and prints a code; `supervillain key link <code>` on the new device redeems it. Redemption accepts either code kind (the backend knows what a code maps to), so the guest upgrade box needs exactly one line of instruction. CLI first-run setup offers the same call conversationally. Device-link codes are single-use, 15-minute expiry (both machines are at hand). The CLI reaches the backend over the same authenticated-HTTP path `publish` needs — shared machinery.

**Decision: guest adoption codes are minted at session start and shown in the upgrade box.** Only the gateway knows a session is `guest:X`, and guests have no reconnect continuity (ADR-0004), so the handle must be minted during the live session: the gateway (as trusted party) has the backend mint a single-use adoption code bound to `guest:X`, and the can't-miss upgrade box displays it — install the CLI, `supervillain key link <CODE>`, keep tonight's history. Adoption codes live **7 days** (guest-first means no mid-session install pressure) at ~8–10 base32 chars of entropy; the guarded asset is one session's chat and rolls. A guest may instead just bring a key next time (ADR-0004's path, unchanged) — continuity going forward, no adoption until they install the CLI and link.

**Decision: the backend registry is the truth; rooms materialize linking as log events.** The backend service (which the definition already makes the code registry) holds the authoritative key-equivalence graph. But seats and attribution are log-derived and a joiner's fold must equal the host's, so any equivalence that affects a room must land in that room's log: a `core.actor-linked` event whose envelope actor is the redeeming key and whose payload names the absorbed actor (`{ linked: "guest:X" | "<64hex>" }`). The fold unions `envelope.actor` with `payload.linked`; one event type serves adoption and device linking alike. Historical events are untouched — old `guest:X` entries stay raw; the fold makes them reachable (prototype-validated). The event arrives as a **gateway-stamped submission** — actor ≠ connection is exactly the trusted-stamper power ADR-0004 grants.

**Decision: linking facts travel over the registration connection.** At room registration the gateway delivers pending linking events for the room's actors (the redeemed-on-Tuesday case); when an unknown key joins, the host queries the gateway over that same connection — linked to anyone in my log? — appends the event, and seat claiming proceeds. No new trust relationships and no host→backend channel: an unregistered room trusts nobody and therefore links nobody, consistent with ADR-0004. GM roaming falls out with no mechanism of its own: the laptop key unions into the GM's identity, and idempotent log-derived seat claiming returns the GM seat.

**Consequences:** the registration protocol grows two duties (pending-linkings delivery, unknown-key lookup); the gateway becomes the bridge between the two deployables for identity data — how gateway and backend share the registry is an internal seam deliberately left to the backend-data-layer decision ([#32](https://github.com/oscabriel/supervillain/issues/32)); the CLI gains a `key` noun and an authenticated backend path.

**Revisit triggers:** passkeys (v3) join the same equivalence graph via the same primitive — if the browser session can't be modeled as one more linked key, that is a definition problem, not a patch here. Unlink/revoke is deliberately undesigned at v1 (nothing in the definition requires it; a compromised key demands it eventually — definition patch, not a hack). Guest reconnect-as-same-guest remains deliberately absent per ADR-0004.
