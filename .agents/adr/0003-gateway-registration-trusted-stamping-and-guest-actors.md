# Room registration lives in room-wire, the gateway is a trusted stamper, and guests are `guest:` actors

Issue #9 builds the SSH door, which surfaces three decisions the definition placed but never mechanized: how a room name gets INTO the gateway's registry, how the gateway can submit commands for players it proxies when ADR-0001 binds actors to connections, and what actor string a keyless guest carries.

**Decision: registration is a room-wire protocol.** `registerRoom` (the CLI's client half) and `serveRoomRegistry` (the gateway's serving half) join the RoomStore wire story in `packages/room-wire`, sharing its codec and accept-loop; the gateway injects a `RoomRegistry` implementation (bun:sqlite) so the wire layer stays storage-free. `supervillain create --name <room> [--gateway <addr>]` dials the gateway and registers `name → host address`; ownership is the registering connection's authenticated key (ADR-0001 applied to registration), so the same GM re-registers freely — a restart re-mints the door — while another key claiming the name is rejected. Room names are pinned to 1–32 chars of lowercase a–z, 0–9, and interior hyphens, validated at the wire.

**Decision: the trust flows from the GM's registration act.** `ServeRoomStoreOptions` gains `trustedStampers`: connection identities allowed to submit commands whose actor differs from the connection's key. The only stamper a v0 host trusts is the gateway it just registered with — `registerRoom`'s receipt carries `gatewayId` (the mutually-authenticated peer of the registration dial), and `create` passes exactly that to `serveRoomStore`. An unregistered room trusts nobody; ADR-0001's actor check is unchanged for everyone else. The gateway authenticates players itself at the SSH edge (ed25519 publickey with signature verification) and stamps their actor onto proxied submissions — the same trusted-party role the SSH terminating point already plays for rendering.

**Decision: guest actors are `guest:` plus 12 hex chars,** minted per SSH session. The prefix keeps guests structurally disjoint from 64-hex key actors (no collision, trivially recognizable), and the string lives in envelopes like any actor, so v1's linking event can adopt it as-is. The keyless door is SSH `keyboard-interactive` accepted with no prompts (`none` must be rejected or every client would land as guest before offering its key); non-ed25519 public keys fall through to the same guest path. The upgrade box renders before the guest sits down and waits for a keypress — can't-miss by construction.

**Revisit triggers:** if the browser bridge (v3) needs registration or stamping over a second transport, that is the codec/dial split ADR-0001 already names. Guest reconnect-as-same-guest (a session-scoped cookie of some kind) is deliberately absent — a guest who wants continuity brings a key; if real play demands more, that is a definition patch, not a gateway hack.
