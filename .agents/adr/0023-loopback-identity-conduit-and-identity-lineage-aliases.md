# The identity hop made concrete: a loopback-only conduit, and lineage aliases so linking never orphans an artifact

Resolved on [The publish API (#104)](https://github.com/oscabriel/supervillain/issues/104), 2026-07-30. [ADR-0013](./0013-server-data-layer-gateway-owned-identity-and-two-stores.md) put the key-equivalence graph in the gateway and gave the backend identity through a narrow TypeScript interface with a _remote_ implementation — "a local call to the gateway" ([ADR-0020](./0020-web-stack-tanstack-start-pages-mounted-hono-api-one-process-on-the-vps.md)) — without pinning the call's mechanics. [ADR-0009](./0009-capability-url-and-publish-contract.md) pinned the linking edge: two linked identities that each published the same (type, name) never lose either URL; re-publishing that name errors, listing both, until the owner revokes one. Implementing #104 forced both loose ends concrete, and one of them adds a durable row class to the gateway store — which is why this is an ADR and not a code comment.

**Decision: the conduit is loopback-only HTTP on the gateway — a same-box seam, not a gateway HTTP surface.** `apps/gateway/src/identity-conduit.ts` answers `POST /identity/resolve` on `127.0.0.1` — the bind host is deliberately not configurable — at port 3002 in the operated role (ephemeral in embedded/test gateways). It answers three facts per key: current identity, owner-identity lineage (below), and revocation. [ADR-0005](./0005-key-linking-backend-registry-gateway-conduit-and-in-log-linking-events.md)'s amendment stands unbent: "the gateway exposes no HTTP surface" is about surfaces — doors, ports Caddy proxies, anything a client or attacker can reach — and the conduit is none of these; it is unreachable off-box by construction, never proxied, and carries no authority a local process does not already hold (the graph is world-readable facts about which keys are one person, and the hosted box's other process is ours). The seam's contract remains the TypeScript interface, exactly as ADR-0013 framed it: `IdentityDirectory` stays synchronous and untouched; the awaited face (`AsyncIdentityDirectory.resolveKey`) lives web-side, where its docstring always said the awaiting belonged; the HTTP shape underneath is an implementation detail either side may swap without a protocol negotiation. The hop lands only on the cold publish path — authentication of `/a/*` reads never touches it — and its failure mode is ADR-0013's accepted one, now with a status code: the publish API answers 503 when the gateway is unreachable, honest rather than mysterious.

**Decision: the permitted lone-key move records lineage — `identity_aliases` joins the gateway store.** ADR-0005's amendment allows exactly one graph mutation that deletes an identity: a lone key owning nothing is silently moved into the redeeming identity. "Owning nothing" was checked against what the gateway can see — sibling keys and rooms — but the gateway deliberately knows nothing about published artifacts (two stores, ADR-0013), so a lone key that had published could be moved, its old identity id deleted, and every artifact keyed by that id would become permanently unlistable and unrevokable while its capability URLs stayed live: exposure `publish list` exists to make visible, made invisible by the one mutation that was supposed to be safe. The fix is one narrow durable fact: at the move, the deleted identity id is written to `identity_aliases (former_identity_id → current_identity_id)`, earlier lineage is flattened onto the new current identity, and the conduit answers `ownerIdentitiesOf(key)` as current-first-then-former. The backend queries artifacts across that set — which is precisely what makes ADR-0009's linking edge mechanical: two live rows for one (type, name) across a caller's lineage is the collision, answered 409 with both URLs. This is lineage, not a second graph and not identity merging — nothing resolves _through_ it on any authentication path, and the mirror invariant is untouched (identity ids are not game content). ADR-0013's durable list gains the row, corrected there in place.

**Decision: two API-shape details, recorded so they are deliberate.** The authenticated-HTTP shape (ADR-0005: "challenge–signature, as the pipe does") lands as three request headers — `supervillain-key`, `supervillain-challenge`, `supervillain-signature` — over a one-use 32-byte challenge with a two-minute TTL, held in process memory only (a restart voids outstanding challenges; the CLI simply asks for another), verified as ed25519 over a domain-separated message (`supervillain/publish-http/1`). And revoke gains a narrow collision selector: when lineage produces two live rows for one (type, name), `DELETE` without a selector answers 409 listing both URLs, and may carry the `capability` to name the one to kill — the pinned CLI noun stays `(type, name)`; the selector exists only because "revoke one" must be executable without the server silently choosing a row.

**Consequences:** ADR-0013's durable list gains `former identity id → current identity (lineage aliases) | gateway store | this ADR`, corrected in place with a dated note. The gateway's operated role owns loopback port 3002 beside the pipe's 8443; the web deployable reads `SUPERVILLAIN_IDENTITY_CONDUIT_URL` and defaults to `http://127.0.0.1:3002`, so #108's one-box deployment needs no new configuration. The conduit's spec lives in the gateway's test lane, as #104's done-when required.

**Revisit triggers:** posture 2b (self-hosted web co-located with a self-hosted gateway) uses ADR-0013's _local_ implementation and never starts the conduit — if it ever wants the conduit instead, that is a smell, not a feature. Moving the web surface off-box would turn this same-box seam into a real cross-network identity protocol — exactly the cost ADR-0020 declined serverless hosting to avoid, so it reopens that decision, not just this file. If lineage ever needs to resolve on an authentication path, or a second consumer appears, the "not a second graph" line above is the thing under pressure — stop and re-decide rather than widen it quietly.
