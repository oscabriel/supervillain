# Pixel-glyph rendering tier: baked MonoMek atlas, quadrant rasterization, pixel-default with text fallback

> **Amended 2026-07-30 by [ADR-0021](./0021-mekmode-atlas-octant-packing-and-4x3-tiles.md):** atlas source MonoMek → MEKMODE, quadrant → octant packing, one tile 4×4 → 4×3 cells. The tier decision, defaults, scope, and everything below the renderer stand.
>
> **Scope fence added 2026-08-04 by [ADR-0030](./0030-closed-pane-frames-tab-traversal-side-rails-and-contextual-key-help.md):** the Table's closed Pane frames are tier-neutral one-cell light box drawing. The ornamental-chrome allowance does not license 4×3 atlas dings in Pane borders or titles; pixel ornament remains Map plus isolated threshold art such as the Lobby wordmark.

Resolved 2026-07-21, in-session grilling following [#39](https://github.com/oscabriel/supervillain/issues/39)/[ADR-0006](./0006-core-owned-battle-maps-and-inline-map-capture.md). The product wants the Caves-of-Qud / MonoMek "enhanced ASCII" identity without shipping a font — an unrealistic ask over ssh. Technical grounding (OpenTUI clone @ `a0b9064`, MonoMek metrics, geometry math) lives in the local research doc `.agents/research/monomek-pixel-glyph-rendering.md`; wire and buffer facts inherit from the [#38](https://github.com/oscabriel/supervillain/issues/38) FrameBuffer research.

**Decision: the map surface gains a pixel-glyph rendering tier, built from a baked 1-bit glyph atlas.** MonoMek (CC0, by MEK.txt) is rasterized **at build time** by a hand-run bake script into committed 1-bit bitmaps — a data-only package with zero runtime font dependency. At render time, core chrome composes each visible tile/token glyph into Unicode quadrant-block characters by direct cell writes: each 2×2 bit block maps exactly to one of 16 quadrant chars plus theme-token fg/bg. For 1-bit input this reduction is lossless. One map tile = one glyph = **4×4 terminal cells** (aspect-corrected 8×8 bake); the map region becomes a scrolling viewport (~45×13 tiles at 188×60). Plain ANSI output — works over bare ssh into any modern emulator; no image protocols (OpenTUI emits none at this commit anyway).

**Decision: scope is the map surface plus ornamental chrome — never body text.** Map terrain and tokens render pixel-glyph; a small set of chrome set-pieces (wordmark, border/divider dings) may too. Chat, log, sheets, menus, and all prose stay real terminal text: atlas-rendered prose would leave ~11 legible lines on a full screen and break copy/paste, search, and screen readers. (Players who install MonoMek locally get the aesthetic on real text for free — a docs note, never a requirement.)

**Decision: pixel mode is the default; text mode is a per-session toggle, no capability detection.** First contact delivers the product identity. ADR-0006's rendering (one map cell = one terminal cell, author's legend characters) is unchanged as the **text tier** — the fallback is the source format, since map files are characters + legend and every atlas entry is keyed by the character it depicts. The toggle is a keybind; detection is rejected as guessing (no reliable probe for quadrant-glyph font coverage; the failure mode is legible tofu plus one keystroke). No preference persistence at v1 — that's unopened scope.

**Decision: the bake is build-time codegen with recorded provenance.** Script (run rarely, by hand) rasterizes the OTF at a chosen ppem, thresholds to 1-bit (MonoMek is a "non-pixel-perfect" vector monotype — the grid must be found, not assumed), resamples to quadrant geometry, and emits a generated module whose header records font/version/author/license/source/date. CC0 imposes no obligation; we record anyway — the first concrete datum for [#48](https://github.com/oscabriel/supervillain/issues/48). Runtime font parsing and hand-authored glyphs are rejected (dependency for nothing; discarding a finished CC0 glyph set).

**Decision: this changes nothing below the renderer.** Same `core.map-*`/`core.token-*` events, same map file format, same authority rules, same publish contract; host and gateway never see the atlas; the dependency lattice is untouched (atlas is data-only, consumed by the render side). **The ANSI-16 contract stands**: 1-bit bitmaps + theme-token colors stay inside exact-ANSI-16, and ADR-0006's "richer-than-ANSI-16 palette + double-width cells" churn row is explicitly **not** fired by this decision.

**Commitment level: v1 target, slippable by construction.** Because the text tier is complete and identical in data and interaction, "pixel mode slips out of v1" is a one-line churn entry, not a redesign. The direction is decided now — before visual proof — on source-verified mechanics; the battle-map rendering prototype ([#29](https://github.com/oscabriel/supervillain/issues/29)'s anticipated ticket) is scoped as _validate the geometry and the look_, not _decide whether_.

**Consequences:** the repo gains a glyph-atlas package and a bake script; core chrome's map region gains a mode switch and a 4×-scale viewport; the prototype ticket gains a concrete checklist (ppem/threshold tuning, quadrant-vs-half-block comparison, ANSI-16 byte verification, default-legend art pass); the docs surface gains a "use MonoMek locally" note; #48 gains its first provenance datum.

**Revisit triggers:** the prototype says the resampled glyphs look bad at 4×4 cells on real terminals (→ text tier ships as default and this ADR's pixel default is struck); real demand for pixel-glyph _body_ text (rejected here — would need its own justification); preference persistence arriving product-wide (→ the toggle may persist); the half-block 8×8-cell variant winning the prototype comparison (geometry amendment, same architecture).
