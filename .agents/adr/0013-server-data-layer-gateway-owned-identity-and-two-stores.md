# The server data layer: gateway-owned identity, two stores, SQLite both sides

Resolved on [Backend data layer: DB and ORM (#32)](https://github.com/oscabriel/supervillain/issues/32), 2026-07-25. [ADR-0012](./0012-outbound-only-hybrid-drop-iroh-host-dials-out.md) centralized reachability but left the server-side data layer as fog, and its own text carried a contradiction: NQ-3 assigns identity duties to "the backend" (revocation marking, identity resolution) while NQ-9 makes the self-hosted gateway **the same single compiled binary** with no company backend at all, and calls that posture first-class. [ADR-0005](./0005-key-linking-backend-registry-gateway-conduit-and-in-log-linking-events.md) had already delegated "how gateway and backend share the registry" to this ticket. The reframing that resolved it: **both** deployables must resolve key → identity — the gateway to authenticate every pipe dial and SSH session, the backend to key published artifacts by owner — so the equivalence graph is shared-truth state with two readers, one of which must work when no backend exists.

**Decision: the key-equivalence graph is gateway-owned.** It lives in the gateway's SQLite alongside the name registry and the ADR-0008 presentation-prefs table. ADR-0005's "the backend service holds the authoritative key-equivalence graph" is **corrected here** — and this corrects an inconsistency already in the record rather than overturning a consensus: closed ops ticket [#40](https://github.com/oscabriel/supervillain/issues/40) listed its precious state as "the registry DB (name→NodeId registrations + the key-linking graph); the backend DB (published artifacts + capability URLs)", i.e. it had already put the graph in the gateway. Four reasons this is the right home. Identity resolution sits on the **authentication** path — every Host pipe dial and every SSH session — so a cross-service hop there is latency and a failure mode on the hottest surface, while publish-ownership lookup is rare and human-initiated and can afford one. ADR-0008 already made the gateway store identity-keyed durable data (prefs keyed by _resolved_ identity), so the gateway is already an identity-resolving process; this admits what is true rather than adding a lookup. It makes NQ-9 work by construction instead of by exception. And revocation becomes a local read the gateway can perform with our servers unreachable — the point of an always-on homelab box. Consequences ride along into ADR-0005's mechanism: **`key link` targets the gateway, not the backend** (ADR-0005 routed it over "the same authenticated-HTTP path publish needs"), and the gateway **mints guest adoption codes itself** rather than asking the backend to mint them — one fewer trust hop, and the only shape that works with no backend.

**Decision: self-hosted web and publishing (posture 2b) is out of scope for v1, and deliberately architected for.** Nothing in the definition forbids a self-hoster running the web role; nothing promises it either — the self-hosting promise is scoped to the gateway everywhere it appears ("one forwarded port + DDNS, the exposed protocol is SSH"; "no CA, domain, or reverse proxy ever required"). The blocker is not our code: **browsers do not do trust-on-first-use.** NQ-9 and [#64](https://github.com/oscabriel/supervillain/issues/64) build self-hosted trust on a pairing code carrying a certificate fingerprint, pinned by _our own CLI_; a fingerprint cannot be pinned into a recipient's browser, so a capability URL served from a homelab box on a self-signed cert produces a full-page security warning for every recipient. Self-hosted publishing therefore requires a real domain and a real certificate — precisely what NQ-9 says is never required. It is not a feature withheld but a materially heavier operational commitment, and bundling it into "one forwarded port" would misrepresent it. **Standing requirement so this stays cheap to add:** because the graph is gateway-local, a future web role co-located with a self-hosted gateway reads the same store in the same process — adding posture 2b is a dependency, never a data migration. Deliberate fog was rejected: a self-hoster who assumes publishing is included and builds around sharing logs discovers otherwise at the worst moment, so the docs state the domain requirement plainly.

**Decision: the hosted gateway doubles as a free identity service.** Publishing is hosted-only at v1, and the graph belongs to whichever gateway you use — so a person who self-hosts their gateway and publishes to our web links their keys with us as well. Identity is **per-gateway**: for the default hosted posture this is invisible (one identity, no extra step); for the self-hosting cohort that publishes it is one setup step, once. The alternative of keying publish ownership by **bare key** was rejected because it forfeits ADR-0009's deliberate decision that "publish from the desktop, revoke from the linked laptop" works. Accepted honestly: that cohort holds two identity records, and a new laptop is linked in both places; the CLI should make that one prompt rather than two rituals, and the docs name the seam rather than hiding it.

**Decision: two stores, with identity reached through an interface — not a protocol.** The gateway store holds the name registry, presentation prefs, the key graph, revocations, and link codes; the backend store holds published artifacts, capability tokens, and dead-token tombstones. The backend obtains identity via a narrow **TypeScript interface with two implementations** — _local_ (in-process, straight to the store) and _remote_ (a local call to the gateway). The gateway uses local; the hosted backend uses remote; a future self-hosted web role uses local. Because ADR-0013's first decision keeps the graph gateway-side, the hop lands only on the cold publish path and never on authentication. One shared store, and a shared-schema module both processes import, were both rejected for the same reason: they weld the two deployables to one machine, turning #30's "one box at launch" from a deployment choice into an architectural requirement and blocking any later move of the web surface. The interface framing (not an HTTP contract) is what keeps posture 2b an in-process implementation. Accepted cost: publishing fails while the gateway process is down — a new failure coupling, stated rather than discovered, and a near-non-event given both are supervised on one box and the product is down anyway.

**Decision: linking facts are derived on demand, never queued.** ADR-0005's "at room registration the gateway delivers pending linking events for the room's actors" is read as _derive_, not _store_: the Host sends its own actor list at registration (it has one, from its own log), the gateway resolves those against the graph and answers, and **no per-room queue, delivery bookkeeping, or acknowledgement state exists**. The graph is already the complete truth about who is whom, so a queue would be a second staler copy of a computable fact. This is what keeps NQ-11's "no durable game state at the gateway" a clean line rather than one with an asterisk — the gateway never stores room contents, and the offline-room case needs no mechanism at all. Accepted cost: registration carries the room's actor list, so the gateway sees actor identifiers transiently while storing none.

**Decision: SQLite on both sides.** The gateway's engine was already pinned (`bun:sqlite`, directly, no ORM — product-definition §The data edge). The backend's is now SQLite too. The workload is the argument: publishing is one write per human action and reading a capability URL is a single indexed lookup by token — SQLite's best shape — and #30's resolution reached the same conclusion when it rejected Durable Objects ("SQLite on the same VPS does this with no second platform"). Postgres was rejected as a second process to install, supervise, back up, and upgrade on one box, buying concurrent write throughput nothing needs. **This fires [#40](https://github.com/oscabriel/supervillain/issues/40)'s conditional: Litestream continuous replication is now unconditional work**, with restic demoted to belt-and-braces. Snapshot documents (10 MB cap) are stored as **files on disk under `/var/lib/supervillain/`** with rows pointing at them, never as blobs in the database — the tree #40 already backs up, and it keeps the database small enough to replicate continuously.

**Decision: Drizzle in the web backend; raw SQL in the gateway.** This cashes the churn-ledger row "Drizzle-or-similar ORM | web backend". The boundary is the deployable, not the table count: the gateway — hosted _and_ self-hosted — keeps hand-written prepared statements, so **the binary users download never carries Drizzle**; the hosted-only web backend gets typed queries and typed rows, which is real headache saved even at three tables. The standing constraint survives unbent: server DBs remain lookup/index state and **ORM pressure must not develop** — Drizzle is adopted as a typed query layer, and its relational/ORM-ward modes are not the licensed part. Accepted cost in the gateway: raw statements return untyped rows, so row shapes are hand-written and can silently drift from the schema; the mitigation is that the store is small and its row types live beside its migrations, where drift is visible in review.

**Decision: one migration mechanism for both stores.** The existing `PRAGMA user_version` + idempotent-steps runner (`apps/gateway/src/migrate.ts`, 22 lines) governs the backend store too. **drizzle-kit is not adopted.** monorepo-stack's "drizzle-kit is not the answer to it" was written about the gateway and does not automatically transfer, so it is decided here on its own merits: the benefit Drizzle earns is typed queries, fully available without its migration tooling, whereas drizzle-kit brings generated migration files and its own notion of schema truth alongside a runner we already trust — and two mechanisms means every future schema change begins with "which store, therefore which ritual," small friction paid forever. Accepted cost: the Drizzle schema definition and the SQL that creates those tables are two artifacts that can drift, so a **startup-or-test-time assertion that the schema matches the definition** is required — turning silent drift into a loud failure.

## The durable list, per owner

| Durable state | Owner | Source |
| --- | --- | --- |
| name → owner identity | gateway store | NQ-4 (replaces the `rooms` table's dead `address` column) |
| resolved identity → presentation prefs | gateway store | ADR-0008 |
| key → identity (the equivalence graph) | gateway store | ADR-0005, relocated here |
| revoked keys | gateway store | NQ-3, [#59](https://github.com/oscabriel/supervillain/issues/59) |
| link codes (device 15 min, adoption 7 days) | gateway store | ADR-0005 — 7-day codes must survive a restart |
| gateway ed25519 host key | file, not a row | #40 (precious; escrowed off-box) |
| (owner identity, type, name) → snapshot document | backend store + file on disk | ADR-0009 |
| capability tokens | backend store | ADR-0009 (OG image URLs derive from these) |
| dead-token tombstones | backend store | ADR-0009 — revoke kills a URL _forever_; a later publish mints fresh, never resurrects |

**The mirror — never durable, anywhere, and testable as an invariant:** the per-Room fold, reconnect snapshots, session buffers, `name → current pipe`, all guest session state, and every form of game content (payloads, chat, rolls, sheets, maps) including in logs, metrics, telemetry, and crash reports.

**Consequences:** ADR-0005 gains a dated correction relocating the graph and re-targeting `key link` and adoption-code minting at the gateway; ADR-0009's publish decisions survive unchanged with only ownership resolution moving to the interface; ADR-0012's NQ-3 (revocation home) and NQ-11 (durable list) gain per-owner attribution. `product-definition.md` gains corrections at the data edge, the supervillain.app-durably-stores list, the self-hosting scope (publishing is hosted-only at v1), and the Drizzle churn row (now cashed). `monorepo-stack.md`'s lattice rule 6, gateway-store bullet, and migration-discipline bullet are corrected. The dependency-cruiser rule `bun-sqlite-only-in-gateway` is **reworded** — its stated intent "the gateway is the only thing touching a DB" stops being true — and its **bypass closed**: the rule matches `^bun:sqlite$` while `doNotFollow: node_modules` means a Drizzle SQLite driver would import past the fence without firing. **ADR-0005 has no implementation** (commit `07e9787` touched two docs; zero source references the graph, a linking event type, or a `key` verb), so a new implementation issue is filed as the missing foundation — it unblocks #59 and retires #57's bare-key deferral, after which GM roaming works and NQ-3/NQ-4 are satisfied. Litestream graduates from conditional to required.

**Revisit triggers:** **signed link certificates** — replacing ADR-0005's database-row equivalence with attestations key A signs about key B, making the graph portable and verifiable by any party without a shared store — become the answer if cross-gateway identity portability is ever really demanded (it dissolves the two-identity-records cost above; deferred now because revoking a signed statement is materially harder than flipping a column, and #59 wants revocation simple). Drizzle's scope widens beyond a typed query layer only when the backend store exceeds roughly six tables or needs its first join. Posture 2b opens on real self-hoster demand for publishing, accepting the bring-your-own-domain requirement. The one-store option returns only if the two deployables are ever deliberately co-located for good.
