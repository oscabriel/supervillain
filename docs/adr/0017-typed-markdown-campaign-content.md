# Campaign content is typed Markdown: Schema frontmatter, a player-safe body, GM notes that never leave the host

## Decision

Beside the YAML sheets, a campaign holds Markdown files with YAML frontmatter: `table.md` (the front page: `title`, `pitch`, the opening scene `start`, `sync: auto|manual`, and optionally `rules`), `scenes/`, `npcs/`, `handouts/`, `items/`, `ancestries/`, `classes/`, `abilities/`, `party/` and `monsters/*.md`, each named `<id>.md`. Every kind's frontmatter is a strict Effect `Schema` in `apps/supervillain/src/content/frontmatter.ts`, annotated with descriptions and examples and decoded with `{ errors: "all", onExcessProperty: "error" }`; `party/` and `monsters/` follow the campaign's rules (the Draw Steel and PF2e kinds are the `heroes/*.yaml` and `monsters/*.yaml` fields plus links by id, so a YAML sheet moves into Markdown unchanged). The body splits on ATX and underlined headings (`markdown.ts`, with the fence and block rules `blocks.ts` shares with `prose.ts`). HTML comments are removed first, fence-aware, so a commented-out heading never splits a section and an unclosed `<!--` hides the rest of the file. Fences follow CommonMark: a backtick fence's info string holds no backtick, and a fence still open at the end is a problem (`unclosed code fence`) whose opener is read as text and whose rest is withheld from players. `isGmHeading` strips emphasis, code marks and edge punctuation, then matches `gm`, `gms`, `game master`, `gamemaster`, `dm`, `dms`, `dungeon master`, `director notes`, `secret` or `secrets` at the start, on a word; such a heading (even `##GM Notes` with no space, itself a problem) opens a GM block that only an ATX heading of the same or a higher level closes. Underlined headings need a plain paragraph above them, never a list item, quote, rule or the tail of a comment, and inside a GM block a `---` or `===` under text is GM text and a problem, never a heading. A heading that mentions the GM without starting with it, and a bold or colon-ended line that reads like a GM heading, are problems too. `prose.ts` parses the player-safe rest into deterministic `Prose` blocks (paragraph, preformatted, list, quote, heading), cleaned with the domain's `cleanText`; `## Read Aloud` is kept apart. `loadIndex` reads every file (8 at a time, each refused past 64 KB, or when it isn't a regular file, by `stat` before it is read; art, maps and `table.md` are read the same way), never throws, and collects `{ file, field?, line?, message }` problems; `crossCheck` follows every link by exact id (scene to npcs, handouts, items, map, monsters and next; npc to monster and portrait; party to ancestry, class, items and abilities; handout to map and art; `table.md`'s `start` to a scene), reports a card's art or map that won't read or draw,, and flags an id in both `heroes/` and `party/`, or `rules` named in both `campaign.yaml` and `table.md`. `supervillain check` reports these whether or not the table has a log yet; the host refuses to open (`ContentInvalid`) while any remain. `supervillain schema [dir] [--out] [--draft 2020-12|07]` writes `<kind>.schema.json` per kind from the same schemas (`Schema.toJsonSchemaDocument`, `JsonSchema.toDocumentDraft07`) and an `index.json` of file patterns, for editors. At the table, `CampaignContent` holds the last campaign that checked out in a `Ref`: its index and every file's player-safe `StageCard`, built once by `checkWith` while validating. `card`, `cards`, `gmNotes`, the prep catalog and the Markdown sheets all read that snapshot, never the disk, so what `/show`, `/sync`, `/pc` and the prep panel see is always one validated read; only `ContentWatch` (and the prep panel's reload, through it) replaces it, with `accept`, and only when the fresh read has no problems. YAML sheets and maps are still read from disk on each load. The Sheets port carries cards and sheets into commands during `intake`.

## Why

- A GM already writes prep in Markdown; the table should read it as it is, with a schema to catch a typo before the session rather than at the table.
- One schema gives the decoder, the error messages and the editor's JSON Schema, so they cannot drift apart.
- GM notes live in the same file as what players see, so the split must be structural and conservative: a fenced example of a GM heading is text, and an unclosed comment hides everything after it.
- Problems are data, not exceptions: one bad file must not hide the other ten problems from `check`.

## What breaks if you change this

- Putting GM notes, or the raw body, in an event or a card sends them to every seat that folds the log.
- Reading files during `decide` or `apply` makes replay depend on today's disk; cards and sheets must ride in the command.
- Letting `check` stop at the first failing file turns fixing a campaign into one round trip per typo.
- Treating headings inside fences as real lets a fenced `## GM Notes` swallow the player text after it, or a real one hide in a fence and leak.
- Letting `---` under GM text end the block, or a commented-out heading split a section, puts the rest of the GM notes on every player's screen.
- Building cards from a second read of the disk lets a broken or half-saved edit reach the table after a good one was validated.
